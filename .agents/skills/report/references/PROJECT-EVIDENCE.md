# 项目证据

## 1. 定位与能力

以 `doc/00-overview.md`、`doc/00-whitepaper.md`、`doc/02`–`14` 和
`.agents/FEATURE-INDEX.md` 为导航,逐项核对源码:

- 通信模型、序列化、传输后端、QoS、安全、zerocopy;
- 录制回放、Proxy/发现、CLI、Viewer/WebViz、C/Python 集成;
- Windows/Linux/macOS/QNX/Android 与 C++17 基线;
- CI、测试、文档、示例、包管理和 Release 工程。

报告必须给出一句清晰定位,并明确 VLink **解决什么、不解决什么**。
区分通信中间件、机器人应用框架、ROS 2 RMW/生态、数据工具链和可视化
平台等不同层级。

## 2. 发展与活跃度

在不打印 remote URL 或凭据的前提下采集:

- `git log` 的 30/90/365 天 commit、活跃日期、作者分布和主要目录;
- tag/release 的频率、最近版本、版本间隔与 CHANGELOG 质量;
- GitHub open/closed Issue、PR、合并时间、未处理时长、贡献者和 CI
  状态;
- 最近变化集中于新功能、缺陷、文档、测试、发布还是内部重构;
- 外部贡献比例、关键模块作者集中度与维护风险。

所有指标写清截止日期和窗口。机器人提交、批量格式化、merge commit 与
实质功能提交要区分;单个作者高产既可能意味着执行力强,也可能意味着
bus factor 风险。

## 3. 成熟度证据

从以下维度分别列证据和缺口:

| 维度 | 证据 |
| ---- | ---- |
| 产品完整度 | 功能闭环、公开 API、工具与文档 |
| 工程质量 | CI 平台、测试层次、静态检查、发布自动化 |
| 性能 | 基准方法、可复现报告、实际对比对象 |
| 稳定与兼容 | SemVer、ABI/线格式、升级与迁移策略 |
| 生态与采用 | 外部用户、集成案例、包分发、贡献者 |
| 治理与可持续 | roadmap、Issue 响应、review、维护者集中度 |

不要运行项目构建或测试;使用仓库已有 CI/报告作为事实,并明确其时间和
覆盖边界。没有公开量产、认证、用户或性能对比证据时不得补想象结论。
