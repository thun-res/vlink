# 评审范围规划

## 建立文件全集

先读 `.agents/REPO-REFERENCE.md`,再以当前工作树实际文件为准。全仓评审
先固化版本控制文件与未跟踪文件全集:

```bash
REPO_ROOT="$(git rev-parse --show-toplevel)"
git -C "$REPO_ROOT" ls-files --cached --others --exclude-standard
```

该命令生成原始清单。应用并记录下述排除项后,冻结的审计内清单才是
覆盖率分母;排除项另行报告。再按公开 API 与核心实现、传输后端、
CLI/C/Python 接口、Proxy、Viewer/WebViz、工程与发布设施、测试/示例、
文档/规则等职责分组。模块和 CLI 名称从清单动态获取,不要在 skill 中
维护固定枚举。根配置、许可证、版本、包配置和 `.github/` 中不属于已列
目录的文件也必须保留在对应任务中。

## 排除与边界

- 默认排除 `thirdparty/`、构建目录中的生成物和缓存。
- 已纳入版本控制的派生文件仍须登记并检查,例如 drawio 导出的 PNG、
  自动生成但被仓库维护的代码或包元数据。
- 用户指定范围时只取对应子集,但要包含与其直接耦合的公开头、测试和
  配置;若扩展范围,在报告中说明原因。
- 改动清单触及第三方时单列,说明来源、是否应直接评审以及为何跳过。
- 二进制、图片等不能逐行审查的文件仍须登记,按来源、配对关系或生成
  流程检查。

## 任务切分

- 一个任务只包含能由同一规则集审查的相邻模块。
- 大模块按子目录或稳定职责继续拆分;传输后端、CLI 工具原则上分别审查。
- C API 同时核对 ABI 与上位 C++ 约束;测试、文档和工程设施不要混进
  核心实现任务。
- 每个任务在派发前附确定的文件清单,结束后才能准确计算覆盖情况。
