# 文档与注释规范

约束所有面向读者的文字:`doc/`、各级 README、头文件 Doxygen、GitHub
Wiki。内容层面的知识在 `doc/` 各章,本文只约束"怎么写"。

## 1. 语言

- 项目维护的 README 与 `doc/` 正文使用简体中文(`zh-CN`);
  `README.en.md` 是根 README 的英文镜像。`thirdparty/`、`builtin/`、
  `prebuilt/`、`packup/licenses/` 与生成内容不在翻译整改范围。
- 公共头文件 Doxygen 与其他语言确有必要的代码注释使用英文;除
  `examples/` 外,`.cc` 不写说明性注释。`examples/` 豁免该禁令,可写
  必要的英文教学注释,详细内容写入对应 README。
- 委派子代理写文档时,必须在指令中显式注明"输出用简体中文"。

## 2. 行文风格

- 极其专业、精炼,理工科思维;范文是 `doc/00-whitepaper.md`。
- 禁止:营销腔、"一句话总结"、"X 秒上手"、"速查卡"式噱头、感叹号
  堆砌。
- 技术断言必须可验证:给出类型/参数/默认值,而不是形容词。

## 3. Emoji 使用

- `doc/` 标题保持所在文档与所在层级的既有样式;使用 emoji 的章节继续
  维持“一标题一 emoji”,白皮书、模板片段和现有无 emoji 的低级标题
  不得为统一外观机械补齐。正文不用 emoji。
- 门户/落地页(GitHub Wiki Home、`.github/wiki/`、官网页面)**允许且
  应当** emoji 美化——这是上一条“正文不用 emoji”对门户与落地页的
  场景化例外,别把落地页的 emoji 全删。

## 4. Doxygen 规则（公开头文件）

- 完整规范见 `.agents/languages/CPP.md` 第 10 节(块形态、标签顺序、行内
  标记、作用域),本文不重复。要点:公共头文件必须英文 Doxygen 注释,
  文件头内容与复杂度相称;关系复杂且图表更清楚时再用 `@par` 表格与
  `@code` ASCII 图。`private`/`protected` 不强制 Doxygen;除 examples
  外,`.cc` 不写说明性注释,只保留许可证头和工具必需指令。
- `internal/`、`impl/` 是实现路径,Doxygen 当前仍会扫描;不作为首选
  直接 include 入口,但进入公开签名或供用户配置的符号仍按公开契约维护。

## 5. drawio 插图风格

成对提交、导出倍率与背景规则见 `doc/15-contributing.md` §15.19.1;
视觉参数以 `doc/images/` 当前图源为准。新图/改图前先打开 2–3 张相邻
主题的 `.drawio` 对照,禁止另建一套风格。

- **字体**:默认沿用 `Helvetica`;代码、标识符和 URL 是否使用
  `Courier New` 跟随相邻图与同层级元素,不要为统一字体机械改图。
- **形状**:模块/步骤矩形使用圆角(`rounded=1`);表格单元格、内存布局
  和细时间线标记可用直角。同层级节点同尺寸、同字号。
- **配色**:沿用现有 Material 浅色系,不自创颜色——
  蓝 `#e3f2fd`/`#bbdefb`(主体模块,强调用 `#1976d2`)、
  绿 `#c8e6c9`(正常流/数据)、琥珀 `#ffe082`(警示/特殊路径)、
  灰 `#eceff1`(外部/底层)、白/`none`(容器与分组框)。同一语义
  在同一张图乃至全套图里必须用同一颜色。
- **排版布局零错误**:元素对齐到网格,同列左对齐/同行居中对齐,
  连线走直角或直线且不穿越节点、不交叉重叠,箭头方向与数据流一致,
  文字不溢出图形边界,间距均匀;导出 `.png` 前缩放检查一遍,有错位
  就回 `.drawio` 修,禁止带着排版错误导出。

## 6. 同步义务

- 公开 API、功能入口或文档结构变化的完整同步范围只在
  `/sync-review` 维护;逐项执行其核对清单,只同步实际受影响项,不适用
  项说明原因。
- **`.github/wiki/` 落地页与 `doc/` 同源**:`index.html` 与
  `assets/js/i18n.js` 中的后端数量/scheme 清单、特性宣称、性能口径、
  API 代码片段,凡 `doc/` 对应内容变更(尤其 `doc/04` 后端表、
  `doc/00` 能力清单)必须同步修改;
  落地页允许 emoji 美化(见第 3 节),但事实数据不得与 doc 矛盾。
- `doc/images/` 中插图为 `.drawio` 源 + 同名 `.png` 导出的配对:改图
  必须先改 `.drawio`,**改完必须立即重新导出同名 `.png`**,禁止只改
  一边;文档描述的架构变了,配图要一起变。导出命令:

  ```bash
  drawio --export --format png --scale 2 \
    --output doc/images/<名>.png doc/images/<名>.drawio
  ```

  使用白色不透明背景,禁止 `-t`;headless 环境确有沙箱错误时才加
  `--no-sandbox`。改动 `.drawio` 的提交里若没有伴随同名 `.png`
  变更,视为遗漏。
- 文档中的代码片段视同代码:必须能按当前 API 编译,遵守
  `.agents/languages/CPP.md`(显式 `vlink::` 前缀等)。

## 7. Qt UI 与 Wiki 前端资产

- 修改 Qt `.ui` 时使用相邻文件的 Qt Designer/XML 结构,保持既有
  `objectName`、signal/slot 接线、翻译属性和资源路径;不得为排版手工
  重写整份 XML。
- 修改 `.github/wiki/` 的 HTML、CSS、JS 时沿用现有组件、DOM 标识和
  i18n key,三种语言同步;不得顺手引入新的前端框架、构建链或依赖。
- 只修改当前功能需要的节点和样式。实际构建、浏览器或 Qt 运行验证仍
  需维护者明确要求;未执行时如实说明。
